# Consolidation Findings: Token Aware Diff Sizing (Phase 11)

## Findings

### F1: The single-version "-y still calls Prompt" guard no longer supplies -y
- **Class**: behaviour
- **Failure**: `TestRegenerateRun_Yes_AlwaysCallsPrompt` was the single-version regenerate's guard for CLAUDE.md seam 4: under -y the engine still calls `Prompt` at the source, target and notes gates, and the presenter does the skip and the echo. Its only -y input was the `true` it passed into `req.Yes`. Task 11-1 deleted that field and dropped the argument, as planned (analysis-tasks-c3 Task 1 lists :240 among the `true` call sites). The test now hands the engine no -y at all. `freshRunDeps` → `regenWriteDeps` leaves `ReleaseDeps.Yes` and `StdinInteractive` false, and the `RecordingPresenter` has no -y of its own, so the run is byte-for-byte a no-flag run that takes the defaults. Since this phase, `ReleaseDeps.Yes` is the only -y a single-version regenerate can read (`deps.attended()`). Suppose a maintainer adds an engine-side `if deps.Yes { return the default }` to `resolveSource`, `resolveTarget` or the confirm. The test still passes, and its name and its failure message ("under -y the engine must still call Prompt at every gate") vouch for something it no longer checks. Nothing else covers it: no single-version `RegenerateRun` test sets `deps.Yes` and asserts the gates fire. The cmd-layer `-y` cases in cmd/mint/regenerate_exclusioncheck_test.go:66 pass both axis flags and assert only the AI calls. The regression would surface for users: `-y` regenerate logs would lose their `source: fresh (-y)` / `target: release (-y)` / `notes: accepted (-y)` echo lines, and no test would fail.
- **Evidence**: internal/engine/regenerate_interactive_test.go:221-254 (the test; :239 `runReq(engine.SourceUnset(), engine.TargetUnset())` with `freshRunDeps(rec, f)`; :233-235 and :245 claim -y), :24-25 (the file header's "-y → the engine still calls Prompt at every gate" bullet); internal/engine/regenerate_write_test.go:579-586 (`regenWriteDeps` sets neither `Yes` nor `StdinInteractive`); internal/engine/notesfloor.go:18-20 (`attended()`, the engine's read of `deps.Yes`); internal/engine/regenerate_interactive.go:240 (its single-version use); the removed input, phase diff of internal/engine/regenerate_interactive_test.go (`runReq(engine.SourceUnset(), engine.TargetUnset(), true)`).
- **Proposed shape**: In `TestRegenerateRun_Yes_AlwaysCallsPrompt`, build `deps := freshRunDeps(rec, f)` and set `deps.Yes = true` and `deps.StdinInteractive = true` (the "-y at a terminal" mode `unattendedModes` names in regenerate_floor_nextmoves_test.go:26-33). Pass `deps` to `RegenerateRun`. The three-gate subject assertion and the AcceptEcho check stay as written. With that change the header bullet and the test's comments are true again, and a deps-keyed engine-side skip turns the test red. No production change.

### F2: The setup guide now sends a regenerate's unwritten notes to on_notes_failure, which regenerate never reads
- **Class**: behaviour
- **Failure**: Task 11-2's new sentence first makes "a release-notes call" the subject, then routes on: "Notes still unwritten follow [release].on_notes_failure: abort loud, ... or fall back to the commit-subject list". The ladder sentences are right for both release and regenerate, because a regenerate's fresh source classifies and halves the same way. The routing sentence is wrong for regenerate. Regenerate never reads `on_notes_failure` (spec §12.3, README.md:165, internal/engine/regenerate_interactive.go:238-239). An attended single-version regenerate is offered the choice whatever the key holds. An unattended one stops with next moves. `--all` skips the version. The guide's only other mention of regenerate, "It rides on the same [release] config", has no exception, so an agent reading `mint setup` has nothing to correct the routing claim. The guide's overview tells that agent to advise users on regenerate too. It will tell a user that `on_notes_failure = "fallback"` makes an unattended regenerate backfill ship the commit-subject list when the AI fails. The user finds out when the backfill exits 1 or reports skipped versions. The README already scopes the same routing to "a release's failed notes call" (README.md:295), so the guide and the README now disagree on it. The old guide text, "On failure, release follows ...", had the same gap if "release" is read as covering its regenerate sub-command. This phase wrote the sentence afresh to route failures "the way the code does" and kept the gap.
- **Evidence**: internal/setupguide/setupguide.go:175-182 (the rewritten routing: "When a release-notes call fails ... Notes still unwritten follow [release].on_notes_failure: ..."), :135-137 ("`mint release regenerate` ... It rides on the same [release] config."); internal/engine/regenerate_interactive.go:238-252 (regenerate's floor ignores the key); internal/engine/regenerate_batch.go (`--all` skip-and-continue); README.md:165, README.md:295; spec §12.3 (line 637: "Regenerate does not read `on_notes_failure`").
- **Proposed shape**: Two edits to `overview()`'s raw string, both flag-free. (1) Scope the routing sentence to the release verb: "A release's notes still unwritten follow [release].on_notes_failure: abort loud, where an attended release is offered …". Then add one sentence after "the one non-AI body.": "Regenerate never reads on_notes_failure and never ships the commit-subject list on its own." (2) At :137, change "It rides on the same [release] config." to "It rides on the same [release] config, except on_notes_failure." The setupguide_test.go pins (`floorOffer`, `floorStop`, `floorMoves`, "the commit-subject list, the one non-AI body", the no-flag list) all still hold.
