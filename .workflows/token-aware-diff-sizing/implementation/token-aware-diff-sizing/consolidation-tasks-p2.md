# Consolidation Tasks: Token Aware Diff Sizing (Phase 2)

## Task 1: A Ctrl-C ends a `regenerate --all` batch instead of skipping versions
placement: phase 2
severity: behaviour

**Problem**: Under `mint release regenerate --all --source fresh`, a Ctrl-C while a version's notes are being written is recorded as a skipped version. `processOneVersion` (`internal/engine/regenerate_batch.go:286-289`) sends every `ProduceBody` error, `context.Canceled` included, to `reportSkip`, so that version is listed as `skipped (notes generation failed)`. Every later version then fails at once on the dead context and is skipped the same way. The batch emits its `RunFinished` summary and `RegenerateAll` returns `collected, nil` (`regenerate_batch.go:197-207, 215-220`), so a `--target release` run exits 0 (`cmd/mint/regenerate_all.go:74-77`) and a script or agent reads the interrupted batch as a finished one with a few skips. On a changelog or both target, `RegenerateAllValidated` goes on to `rebuildBatchChangelog` on the cancelled context (`regenerate_batch.go:150-157`), and the run ends on a `record` stage failure rather than a cancel. Phase 2 made a cancel a contract the notes stage keeps: the wave returns `ctx.Err()` over any earlier chunk failure (`internal/notes/chunk.go:99-101`) and `ResolveFailure` passes `context.Canceled` through unchanged (`internal/notes/resolve.go:69-71`). The forward release and the single-version regenerate (`internal/engine/regenerate_interactive.go:207-210`) both honour it; the batch is the one caller that turns a cancel into a skip. Task 4-14 also assumes a Ctrl-C ends a batch ("one ended by a Ctrl-C, on the way out").
**Solution**: In `processOneVersion`, test the `ProduceBody` error with `errors.Is(err, context.Canceled)` before `reportSkip`, and on a cancel return `RegeneratedVersion{}, nil, surface(p, "notes", err)`, as `RegenerateRun` does. `RegenerateAll` then ends the batch with no `RunFinished`, as a gate decline does; `RegenerateAllValidated` skips the changelog rebuild; `exitCode` maps the error to 1. Update the comment at `regenerate_batch.go:278-285` and the covered-failures list in the `processOneVersion` doc to say a cancel is not a skip. Prove it with a test where `ProduceBody` returns `context.Canceled` for v2: `RegenerateAll` returns an error matching `context.Canceled`, no `ProduceBody` call is made for v3, no `skipped` warn is emitted, and no `RunFinished` event is recorded. Derived from §11.5 (a Ctrl-C aborts cleanly), CLAUDE.md seam 5 (`context.Canceled` propagates unchanged; a cancel is not an AI failure, so §12.3's skip-and-continue floor never applies to it), and the finder's proposed shape.
**Outcome**: A Ctrl-C during `regenerate --all` stops the batch and exits non-zero as a cancel, on every target, with no version reported as skipped because of it.
**Acceptance Criteria**:
- [ ] A `--source fresh` batch over v1, v2, v3 (release target) whose `ProduceBody` returns `context.Canceled` for v2: `RegenerateAll` returns an error matching `context.Canceled` under `errors.Is`. `ProduceBody` is never called for v3 and no v3 release is dispatched.
- [ ] In that same run, no `skipped …` warn is emitted for any version, no `RunFinished` event is recorded, and v2's notes stage closes as a failed `notes` stage (a `StageFailed` named `notes`), the same way single-version regenerate renders a cancelled notes stage.
- [ ] A cancel that the producer wraps in its own error is treated the same as a bare one. The production fresh producer wraps its error as `regenerating fresh notes for <tag>: %w` (`internal/engine/regenerate_fresh.go:67`), so the batch still ends, with no skip warn and no `RunFinished`.
- [ ] A `RegenerateAllValidated` batch with a changelog target, and one with a both target, cancelled at v2: it returns an error matching `context.Canceled`. The end-of-batch rebuild never runs, so `CHANGELOG.md` is not rewritten, no `git commit` or `git push` runs, and no `record` stage failure is rendered.
- [ ] On every target, the cancel's error is an `*engine.AbortError` with exit code 1, so `mint release regenerate --all` exits 1 through `exitCode` (`cmd/mint/main.go:465-471`) and never exits 0.
- [ ] A non-cancel notes failure (a wrapped `ai.ErrGenerationFailed` for v2) is still skipped as before: a `skipped <v2 tag>` warn reading `notes generation failed`, v3 processed, and `RunFinished` listing the skip. The existing skip-and-continue tests in `internal/engine/regenerate_batch_skip_test.go` stay green unchanged.

Every other `ProduceBody` error keeps going to `reportSkip(p, res.Tag, reasonNotesFailed)`.

Their existing error paths carry the cancel out: the loop's `return nil, err` (line 202), the validated entry's early return before `rebuildBatchChangelog` (lines 150-153), and `exitCode`'s `*AbortError` mapping.
