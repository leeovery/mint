  DESCRIPTION: The output a failed git step leaves beneath its line follows one rule: git's stderr, or the error's text when git wrote none. This plan implemented that rule twice and skipped it at the remaining sites. The first implementation is `gitOutput` (release.go:1164), which reads the `*record.GitError` that `record.CommitFile` and `record.IsIgnored` wrap their failed Mutate around. It serves the answers-recording ✗ line and the re-commit warning. The second is a copy inlined in `unstageEdit` (unwind.go:256-259) that reads the Mutate `Result` directly. Every other unwind step throws the `Result` away (`_, err :=`) and passes `err.Error()`. That error is only the runner's `running "git": exited with code N: exit status N` (exec_runner.go:114), since the runner keeps stderr in the Result. The steps that do this are `resetTo`'s hard reset, soft reset and restore (all three were rewritten in task 3-4), `deleteTagIfMade`, and `resetAndAbort`'s call to `resetTo`. Its review deferred moving them to stderr to a banked entry. The same split recurs in internal/record. `CommitFile` and `CommitStaged` both run `git -C dir commit -m subject` through the Mutator, but only `CommitFile` wraps git's stderr. So a commit-msg hook or a gpg signing failure shows its message under the answers commit's ✗ line and nothing under the bookkeeping or changelog commit's.
