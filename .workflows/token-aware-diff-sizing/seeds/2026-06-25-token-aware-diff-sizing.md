# Token-aware diff sizing and graceful oversized-diff handling

When a release has a big diff, `mint release` fails hard with no way forward, and the guard that's supposed to catch this doesn't reliably catch it. There are two facets, one a UX dead-end and one a deeper correctness gap in how "too big" is measured.

**The dead-end.** When the post-exclusion diff exceeds `max_diff_lines` (default 50000), the default `on_notes_failure=abort` path dies with `notes generation failed (diff too large): diff exceeds max_diff_lines (N > M)`. It names the cause and prints the counts, but it offers no hint about what to do next. Nothing tells the user they could raise `max_diff_lines`, add `diff_exclude` globs, set `on_notes_failure=fallback`, or fall back to `--no-ai`. The escape hatches all exist; the user just isn't told they're there, so a big release looks like a wall. Even ahead of any larger redesign, the abort message (and the analogous commit-side skip) surfacing these options would remove the dead-end.

**The deeper gap.** `CheckDiffSize` in `internal/notes/size.go` guards on a raw line count. But line count is only a crude proxy for tokens. The thing that actually has to fit is the assembled prompt — the diff plus the L1 context plus the system prompt — against Claude's context window. So even a diff that sits comfortably *under* `max_diff_lines` can produce a prompt that overflows the model and fails the AI call anyway. The guard catches the extreme case but doesn't actually guarantee "this will fit the model," which is the property we want.

Worth discussing: making the size guard token-aware so the ceiling reflects the real model budget (estimating tokens across system prompt + context + diff rather than counting diff lines). And for genuinely large releases, rather than failing at all, breaking the diff into chunks, summarising each chunk, and then map-reducing or concatenating the partial summaries into the final notes — graceful degradation instead of a hard abort. There's prior art already parked in the tree: `internal/notes/size.go` comments reference a deferred "Change Map + trimmed diff" escalation (trim the diff down to the ceiling instead of failing), which should fold into the same conversation.

Scope note: the guard is shared via `notes.CheckDiffSize` / `notes.ErrDiffTooLarge` and consumed in three places — release, regenerate (per-release skip, reason "diff too large"), and commit (a generate-SKIP). Any change to how size is measured or handled needs to account for all three consumers.
