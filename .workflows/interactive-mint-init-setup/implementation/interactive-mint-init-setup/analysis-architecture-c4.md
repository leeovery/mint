- FINDING: MetadataRow.Default carries display tokens, not real defaults — a latent trap for any non-render consumer
  SEVERITY: low
  FILES: internal/config/metadata.go:102-107, internal/config/metadata.go:119-167, internal/setupguide/setupguide.go:362-371
  DESCRIPTION: MetadataRow.Default is a string that does NOT hold each key's real compiled default — it holds a presentation token in the render convention: "auto" for release_branch/provider (whose real Go default is ""), "shared" for the four per-verb override rows (whose real default is "inherit"), "[]" for diff_exclude, and a blank string for the empty-string and hooks keys. Only the three shared scalar rows (ai_command/timeout/max_diff_lines) carry the actual value, and they are sourced from the exported constants. The struct is named MetadataRow with a field named Default, and MetadataRows() is an exported function on the public config package surface. The drift test guards the (level, key) bijection and spot-checks specific cells, but nothing prevents a future second consumer of MetadataRows() (the spec itself names "upgrade my config" tooling and possible future render targets) from reading row.Default as the literal default and getting "auto"/"shared"/"[]" instead of the real value. The token convention is correct ONLY inside the markdown config-reference render context it was authored for. This is the spec's flagged "type annotation / field contract that would produce wrong results if used outside its current narrow context" — the field's name promises a default, but its value is a render-layer string. Today there is exactly one consumer (setupguide.renderConfigReference) so this is latent, not active.
  RECOMMENDATION: Either rename the field to signal it is a rendered/display token (e.g. DefaultDisplay or DefaultCell) so the contract is honest at the type level, or add a doc-comment-pinned invariant test asserting MetadataRows() is consumed only by the render path. The cheapest fix is the rename — it costs one identifier and the doc already explains the convention. No behaviour change; this hardens the public surface against a misread the field name currently invites.
- FINDING: SoT Default-token convention is enforced only by hand-authored discipline plus per-cell spot tests, not mechanically
  SEVERITY: low
  FILES: internal/config/metadata.go:138-166, internal/config/metadata_test.go:182-236, internal/config/metadata_test.go:254-301
  DESCRIPTION: The (level, key) bijection drift test is genuinely strong — it mechanically derives the schema leaf set by reflection and proves a total bijection, so a key cannot be added/removed/renamed without the SoT failing the build. But the Default COLUMN convention (which keys render "auto" vs blank vs "shared" vs "[]") is hand-authored per row in MetadataRows() and verified only by enumerated spot-check tests (EmptyStringDefaultsRenderBlank, SentinelAutoDefaultsRenderAuto, PerVerbOverridesRenderShared, etc.) that themselves hardcode which keys belong in which bucket. A NEW key added to the schema would pass the bijection (it gets a row) but its Default token is whatever the author typed, and no spot test would necessarily cover it — the convention rule (sentinel-empty => "auto", per-verb override => "shared", empty collection => "[]") is not derivable from the schema, so it cannot be mechanically pinned the way the value-drift pins are. This is an accepted residual the spec acknowledges ("these representations are part of the decided behaviour"), and the per-cell pins are thorough for today's key set, so the exposure is small. Flagging it as the one spot where correctness rests on author discipline rather than being self-contained.
  RECOMMENDATION: No restructuring required for the current key set. If the team wants to close the gap, add a single coverage test asserting every MetadataRows() row's Default is one of the known convention tokens OR a value derived from an exported constant — so a new row with an off-convention token at least trips a guard. Low priority; the existing pins cover all 25 current rows.
SUMMARY: The architecture composes cleanly: the config-metadata SoT is a single well-bounded source that setupguide renders from (config imported in exactly one path), initgen stays config-free, the cmd-layer setup wiring mirrors runVersion, and the configtest test-support package follows the documented internal/testutil pattern to single-source the (level, key) indexer across two test packages. The drift bijection, README tripwire, and structural marker tests form a strong, well-layered anti-drift chain. The only soft spots are both low severity and both about the SoT's Default column — a field whose name over-promises (it holds render tokens, not real defaults) and a token convention enforced by discipline rather than mechanically.
