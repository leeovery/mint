# mint terminal UI design

mint's pretty output is a column of `✓ stage  detail` rows under a 🌿 header line, with a bulleted Plan, the notes behind a `│` gutter, a `[y] accept  [n] abort` bar and a 🌿 footer. agntc's redesign (its `design/terminal-ui.md`) showed what a deliberate look buys, so mint gets one too. Four looks were drawn on 28 Oct 2026 in the Paper file "Mint · terminal look" (sitrep sr-rwmhr1): Ledger, Tree, Rail and Receipt, each on the same six screens. Lee picked **Rail** on 29 Oct: the run drawn as a line from where it starts to where it lands. This doc settles that look and how it's built.

**Scope.** Only pretty output changes. Plain output (`--plain`, or stdout not a terminal) stays byte for byte, every line of it, apart from bugs the switch found and fixed in every mode: a command mint prints to paste now carries the run's own flags and source (one dropped `-m`, so it cut a patch), git's and gh's stderr now show under a failed push, tag, commit or publish, an incomplete unwind names only the steps that succeeded, the heal after a failed publish names the saved copy of the notes that were pushed, a question the input closed on (Ctrl-C, Ctrl-D) says so on the node it asked about, and keys typed before a question is drawn no longer answer it. The notes and the commit message ship exactly as written, as today. Exit codes, behaviour, the questions asked and the keys that answer them all stay. `mint setup`'s guide and the help texts stay. Wording stays, except where a sentence becomes a row and its subject moves into the row's name column.

**The frame.** Every line has a one-space margin. A run opens with one header line: ` mint ─ <verb>` on the left, `mint` bold in the accent and the `─` dim, and on the right, dim, `<where> · v<version>`, where being the repo root shortened to `~/…`. Short of room, the right side gives way the way agntc's does: where is cut from the left, then dropped, keeping the version. A dev build has no version. The layout is as wide as the terminal, between 60 and 100 columns, and 80 when the terminal gives none.

**The rail.** Column 1 is the rail. Every run starts at a station and ends at one, with nodes between them, one per stage:

| Mark | Colour | Meaning |
|---|---|---|
| `◇` | accent | the start station: where the run begins (`v1.3.2  main @ 7c1e0b4`) |
| `●` | accent | a stage done |
| `⠋` | accent | a stage running, braille at 80 ms a frame |
| `○` | dim | a stage still to come; the whole row is dim |
| `?` | accent | a question |
| `✗` | red | a stage failed; its name is red too |
| `!` | yellow | needs a look: a warning, a skipped version, a suggestion not asked about |
| `↩` | accent | the unwind |
| `◆` | accent | the end station: where the run landed (`v1.4.0  released`) |

A node's row is the mark, two spaces, the stage name bold in a 14-column name column, then the detail. A stage that takes time (a hook, an AI call, a push) has its time dim on the right, on the layout's last column. Times read `4.1s` under a minute and `1m 14s` from a minute up; a running stage's clock counts whole seconds. Lines that hang off a node (a hook's committed artifacts, a saved file, captured output) carry the rail's `│` in column 1 and start at the detail column. Between settled nodes the rail is a solid `│` in the accent wherever it shows; below the live node it's a dim `┆`.

**The plan is the rail.** Once the plan is known (after preflight), the stages still to come sit hollow below the live one, each with what it will do (`○ push  main + v1.4.0 → origin, atomic`), and the end station waits dim at the bottom. The bulleted Plan block goes. A stage that won't run (no `post_release` hook configured, a `--notes-file` release's check) isn't in the plan at all. The point of no return is drawn across the rail above the push: `┿━━ point of no return ━━…` to the layout's edge, dim while it's ahead; once the run crosses it, the `┿` takes the accent.

**The live region.** Everything from the live node down to the end station is redrawn in place: up the region's height, erase below, draw it again. The lines above it never change once printed. This is the one place mint moves the cursor up. It never uses the alternate screen and never clears the screen. The renderer wraps hanging text (a body, a long detail) to the width itself, with the rail on every continuation line and no character changed, so every line it writes fits and the region's height is always its line count. A live node's own line is cut instead (its detail is short-lived), and the width is read again at each redraw. The region never grows past the terminal's height less one row (24 rows when the terminal gives none), because the cursor can't go back up into lines that have scrolled away. What wouldn't fit prints as settled lines instead and stays: see Questions. On a run that doesn't land, planned stages that never ran leave the drawing with the region. The region redraws on every event and every spinner frame. Before mint hands the terminal to the editor, the region is erased (today's `SuspendSpinner`), and it's drawn again when the editor exits (`ResumeSpinner`). Warnings already go to the terminal once when stdout and stderr share it, so nothing writes under the region behind its back. The presenter contract changes to match: settled lines never change; only the live region at the bottom is redrawn.

**Progress.** A running stage's spinner sits in its mark's place, with its text dim in the detail column (`running the pre_tag hook…`). The notes of a release written in parts draw a bar: `3 of 4 parts done  ━━━━━━━━━━━━──────` in the accent and dim (up to four parts run at once, so it counts what's done). A part re-cut as too big and the merge show as the bar's text (`part 2 was too big for the model, retrying it as 2 smaller parts`, `merging 4 parts`). The exclusion check runs as its own `check` node before `notes`; its row settles as the check's call ends, saying what it found (`nothing to leave out`, `2 flagged`, `1 flagged, not asked`), and each answer hangs under it as it's given. It runs inside `notes`, which starts first, and the plan marks it so: a dry run never draws it as skipped when notes starts.

**Questions.** A question is a `?` node: the question bold on its own line, then on the line below each key bold in the accent with its action after it (`Y release   n abort   e edit   r regenerate`). The default, the key Enter takes, is the capital, read from the question's own default; a word choice's letter is its first, its meaning dim in parentheses (`F fresh (re-diff + AI)   t tag (tag annotation body)`). The keys line goes once the question is answered. Plain keeps its one-line question and marks the default in its hint: `[Y/n/e/r]`, `[e/K]`, `[fresh/tag/release] (default: fresh)`. Each key answers at a single keypress, as today; keys typed before the question is drawn are discarded, so a stray Enter never answers it. What the question is about hangs off the rail above it, the notes or the commit message indented four behind the `│`, and the plan still waits below it. On an answer the question and what hung above it erase, and the node it asked about settles with the answer as a dim tail: `● notes  written in 4 parts and merged · accepted`. An `e` redraws the body in place before the question comes back, and what mint runs for it (the editor) draws no node of its own. A finished node never changes: an `r` settles the asked node with its tail and its body still under it, so the context `r` asks for is typed with the draft in view, and the stage it runs again draws a new node below, the new body and the question under that. A body too tall for the region (notes longer than the terminal) settles above the question instead: it stays in the scrollback, the question still sits in the region with the plan below it, and on the answer a row under the body records it (`● review  accepted`) in place of the erase. Once any body of a question has settled, each later body for it settles as it's shown (one shown again unchanged doesn't settle twice) and the answer's row goes under the last, so the scrollback always ends with the body that ships. The review shows the body behind the rail; what ships is still the body byte for byte, and `--plain` prints it flush. Under `-y` nothing is asked and the tail reads `· accepted (-y)`. A question the input closes on (Ctrl-C or Ctrl-D, at a keypress or a typed line) fails the node it asks about, `✗ notes  prompt: input closed before a choice was entered`, and the run unwinds; on a node that goes on past it (an `--all` version) that ends the node, its failure drawn under what the question showed and timed by its work. A warning raised while a question is open draws before its answer.
- **The exclusion check's questions** sit inside the check, at its detail column: `? Exclude docs/specs/** from the notes?` bold, the AI's reason with the files it matches and their size dim below it, then `e exclude   K keep`. Each answer replaces its question in place (`docs/specs/** excluded · design documents`), and the line saying the answers were written to `.mint.toml` comes last. Notes stays to come until the last answer, and its clock starts then: no node's time includes time spent waiting on an answer.
- **The notes floor** (`Release without AI notes?`, `c`, `e`, `a`) is a `?` node under the `✗ notes` node and its output.
- **The cached-notes question, and regenerate's `Source?` and `Target?`,** are `?` nodes the same way. Source and Target answer to their words' first letters; where two words share one, the question reads a typed word instead. They sit after the header and before the start station, which draws once both are answered; an Enter that takes the default still records the choice.
- **A typed line** (Source and Target, the context an `r` asks for, and any question when the terminal refuses single keypresses) is read with the question last on screen: the finished lines above it settle, the question prints under them with ` › ` and the cursor after it, and nothing is drawn below it while the line is typed, so the echo lands only on blank rows. The question and what was typed then stay as the answer's record, and the region starts again below. A stage still running leaves the screen while the line is typed and comes back live under the answer.
- **A dry run** shows each question where a real run asks it, with no keys line and a dim `· skipped (dry run)` tail.
- **The notes at the review** are drawn as light Markdown for display only: headings lose their `#` and go bold, list items take `•`, inline code takes the accent, `**bold**` goes bold. What ships, the editor's text and plain stay byte for byte.
- **An abort** says what it kept once, in plain words: `↩ unwind  reset 2 commits · kept your exclusion answers in .mint.toml`, then `◇ v1.3.2  + 1 commit (the .mint.toml answers) · nothing pushed`.

**Failure and the unwind.** A failed stage is a `✗` node with its message. The command's own output follows verbatim behind the node's rail, now red, and a dim `│ ` gutter of its own, so it never reads as mint's words. A saved part-notes path gets a line of its own. A warning is a `!` node. The unwind is a `↩` node naming what it undid, and the rail then returns to the start station: `◇ v1.3.2  back where it started · nothing pushed`, with the run's time on the right. A close states only what mint itself did and where HEAD stands, never how clean the tree is or what a hook did: after a hook has run it claims no more than `nothing pushed` plus what mint wrote, staged or created, and `nothing changed` means nothing that could write had run yet. An unwind that couldn't finish is a `✗ unwind` node with what it did undo and git's output under it; the manual step goes under next. Where its reset failed, the close names where HEAD stands: `◇ main  9f3e2a1 · 1 commit not reset · manual cleanup required · nothing pushed`. Past the point of no return nothing unwinds: a failure there is a `!` node, the end station still reads `◆ v1.4.0  released`, and the exit code is today's (a failed publish or `post_release` warns and exits 0). A run that stops before it changes anything ends at `◇ <start>  nothing changed`.

**Next.** Remedies don't interrupt the rail. A row says what happened; what the reader can do about it prints after the end station under a bold accent `next`. Each item is a lead line, then its command or config line indented five, in the accent, alone on its line: never cut, never wrapped, never in a box, so a triple-click copies it clean. The notes failure's next moves come first, then the exclusion check's suggestions, each with the `diff_exclude` line that acts on it. A remedy a row used to carry (an unwind's manual step, publish's regenerate command) goes here too. A command is the run's own, with its flags, and only the move's change applied: a dry run's stays a dry run.

**The close.** The end station is the close: `◆ v1.4.0  released` and the run's time, with the release's URL on the line below in the accent. Commit lands at `◆ main  a3f9c21 · pushed`, and regenerate `--all` at `◆ done  6 of 7 versions regenerated · 1 skipped`. A dry run ends at `◇ v1.4.0  dry run · nothing changed`, the stages it skipped left hollow above it.

**Colour.** Statuses use the terminal's own colours, so the theme decides how they look. The one brand colour is the accent, mint `#5FD7AF`: in truecolor where `COLORTERM` says so, as xterm-256 colour 79 (the same colour exactly) where `TERM` says 256, and the theme's cyan otherwise. Names are bold, metadata and times dim, rules dim. `NO_COLOR` turns colour off. Meaning never rests on colour alone: every state has its own mark. The 🌿 leaves the output, its place taken by the `mint` wordmark; `commit_prefix`'s 🌿 in the release commit's subject is that commit's text and stays.

**Width.** Every line mint writes fits the width: hanging text and long details wrap inside the detail column with the rail on each line, a live node's own line is cut, and a next command or the release URL, which must stay whole to copy, prints only once the run has ended. Below 70 columns the times drop and a detail goes on the line under its name. Text mint shows verbatim (a body, command output, a detail) is drawn so it can't move the cursor: a tab goes to the next 8-column stop, a carriage return before a line break is dropped, a colour code is removed, and any other control character shows as its Unicode picture (`␍`, `␛`). This is display only: what ships, and plain, stay byte for byte.

**Per command:**
- **release:** start station `◇ v1.3.2  main @ <sha>`. Nodes: version (`v1.4.0 (minor bump)`, today's wording), preflight, `pre_tag` (its command, as each hook's row shows) with its artifacts commit's subject hanging under it, check, notes (naming its source where nothing generated it: the notes file, the commit-subject list), record, the point of no return, push (`main + v1.4.0 pushed atomically`), publish, `post_release`. A dry run leaves every hook hollow, and the preflight hook, which has no node, hangs its skip under `● preflight`. End station `◆ v1.4.0  released`, URL under it.
- **release regenerate `<version>`:** start station `◇ v1.4.0  <source> → <target>`. Nodes: the notes (from the AI, the tag, the release or the file), the review, then `CHANGELOG.md` (rewritten, committed, pushed) and the GitHub release, as the target has them. End station `◆ v1.4.0  regenerated`. Regenerate draws no point-of-no-return rule; its push still ends any unwind. After a publish fails past the push, the heal under next writes exactly the notes just pushed, from a saved copy.
- **release regenerate `--all`:** start station `◇ 7 versions  fresh notes → GitHub releases, then CHANGELOG.md`. A node per version, oldest first; a skipped version is a `!` node with its cause, and its retry command goes under next. Then the `CHANGELOG.md` node (rebuilt, committed, pushed once) and the end station. Today's one block per version, each with its own header, goes from the rail; plain keeps it. A version's notes, progress and question are on its own node. While its publish is still to come the node is still going: anything that settles it (an `r`, a body too tall, a typed read, a narrow terminal) settles it as it stands, and what the version does next draws as a new node; only while it stays in the region does it take its result in place. A failure partway closes with what mint wrote (`2 GitHub releases written · nothing committed · nothing pushed`); an empty set ends at `done  nothing to regenerate`. A version's time is mint's work on it, never time spent waiting on an answer.
- **commit:** start station `◇ main  7c1e0b4`. Nodes: the diff (`4 files · +86 −12`, and what `-a`/`-A` will stage; the counts are the whole commit's, `diff_exclude` or not, and only ever displayed: counting reads the tree once and never fails the run), the message hanging off the rail, `? Commit this message?`, stage (`4 files`), commit, push (`pushed to origin/main`, where the push went). End station `◆ main  a3f9c21`, with `· pushed` after a push (`-p` pushes to the upstream, which may not be origin). A failed `-p` push is a `!` node, `not pushed; the commit is in place`, with git's stderr verbatim under it and `git push` under next; the end station still names the commit, and the run exits 1 as today.
- **init:** the header, then no stations; a `●` row per file created and a dim `○` row per file left alone, its reason dim.
- **version:** ` mint v0.1.2` with `mint` in the accent. Plain stays the bare value.

**The Presenter seam.** `Presenter` stays the one output surface and keeps its events. Its payloads carry what the rail draws, so the presenter still renders only what it's handed:
- **`RunStarted`** carries the header (the command words, where, mint's version) and the start station: where the run begins and its detail. One read-only git call before it gives the branch and the short HEAD.
- **`ShowPlan`** carries the run's stages in order, each with a key, its name and what it will do, and marks the point of no return. The verb/target bullet list goes.
- **Stage events** carry their stage's key, so the presenter fills the right node. A failed stage carries its time.
- **Questions** carry the key of the node they ask about; the exclusion pause carries its suggestion whole.
- **`Unwound`** carries what was undone, what was kept and where the repo ended up as separate fields, not one sentence.
- **`NextMoves`** items become a lead plus a command line, as agntc's remedies are. A move whose flag or config sits mid-sentence stays a lead alone, its wording as today's. Plain flattens them back to today's sentences byte for byte.
- **`RunFinished`** closes every run that `RunStarted` opened, exactly once: how it ended, the end station and the run's time. Plain still writes its line only for today's successful endings.
- **`Quiet`** marks an event that only fills in the run's structure (release's early plan, a node no event settled before): plain's log, pinned byte for byte from before the rail, writes nothing for it.
- **The `Leaf` fields go,** with the 🌿, and so does `StageSuccess.Sentence`, which only today's pretty read.

**Testing:**
- **The renderer** is pure functions from rows, nodes and stations to lines, tested at widths 60, 80 and 100 with colour off, plus exact escape codes for each element with colour on.
- **The live region** is tested by its exact writes: the cursor-up count, the erase, the redraw, and the erase and redraw around the editor.
- **Golden runs** render whole runs at width 100 with colour off and compare against expected text: a release through its review, a release that fails and unwinds, a dry run, a commit with a push, and regenerate `--all` with a skip.
- **Golden frames,** as Switchboard's: each golden run is also kept as `testdata/frames/<name>.txt` and `.ansi`, rendered in process from fixed payloads, so times and hashes never drift. A test parses the ANSI into cells and compares glyph, foreground, background and bold, listing the first 20 cells that differ. An escape it doesn't know fails the test rather than being guessed. `go test <package> -run Frames -update` writes a package's frames again (`./internal/presenter/rail` for the drawing's own, `./internal/presenter` for whole runs). Switchboard's `internal/capture/reference_test.go`, `cells_test.go` and `frames.go` are the model.
- **Plain** keeps its goldens unchanged, and they must pass untouched.

**Pictures.** VHS records the README's art the way agntc's `demo/` does, which is itself Switchboard's: real commands typed into a real terminal, against a world built for them. The same recordings are how a build slice checks its own work: record the verb's tapes, look at the frames, and fix what reads wrong before review.
- **The world** (`demo/world.sh`, built under `/tmp/mint-demo`, which `DEMO_WORLD` moves) has `pigeon` at `~/Code/pigeon` in its own `HOME`, with a bare origin that git reaches as `https://github.com/acme/pigeon` through an `insteadOf` in the world's own gitconfig (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM=1`). Its commits and tags are dated, so their hashes are the same in every recording. `TZ=UTC`.
- **Shims on `PATH`:**
  - `mint` is built from the checkout with a pinned version through `internal/buildinfo`, so the header shows a release.
  - The AI command, set as the world's `ai_command`, answers from canned replies after a short sleep, so spinners show. It picks a reply from what the prompt asks: the exclusion check, a part, the merge or a commit message. An environment switch makes part 3 fail with a usage-limit message, for the failure tape.
  - `gh` answers `auth status` and the release calls.
  - `git` sleeps briefly on `push`.
- **Tapes** share one `demo/look.tape` through `Source`: Lee's Ghostty (JetBrains Mono, Nordfox, `LetterSpacing 0`, `LineHeight 1`, `CursorBlink false`), 100 columns, the shell prompt as `WaitPattern`. Each tape builds the world hidden, then types its command. It waits on output with `Wait` or `Wait+Screen /…/`, and sleeps only to pace a clip. The tapes:
  - `tour`, a clip: a release through the exclusion pause and the review to the end station
  - `failed`: `release -m -y` stopping on the notes and unwinding
  - `dry-run`
  - `commit`: `commit -Ap`
  - `regenerate`: `regenerate --all` with a skip
  - `init`
- **Recording:** `demo/record.sh <name>` deletes the tape's old output, runs `vhs` with `TMPDIR` inside `demo/out/` (vhs writes nothing, and says nothing, when `TMPDIR` is on another volume), then `demo/finalize.sh`. That lays the cursor frames over the text frames, adds a margin and writes a lossless WebP: the last frame for a still, cropped to the rows it drew with the top margin under them, every frame for a clip, plus an MP4. Art is rendered at twice its display width and written straight to `art/`, where it's committed, so a recording's change shows in the diff. `brew install vhs ffmpeg webp`; vhs 0.12 or later.
- **Gotchas** go in `demo/README.md`, as Switchboard's `testdata/vhs/README.md` has them:
  - vhs's browser reaches ttyd over loopback, which an agent's sandbox blocks.
  - A `Set` after any other command is ignored.
  - A path with `/` in it must be quoted.
  - vhs can fail without a word and leave an old frame behind, so `record.sh` deletes the output first and checks that frames exist.
- **The README** leads with the `tour` clip at 840 px, and each command's section gets its still.

**Out of scope:** an ASCII fallback for terminals without Unicode, colour settings, a `--no-color` flag (`NO_COLOR` covers it), and rewording beyond what the rows need.

## Known limits

- **A terminal narrowed mid-run** below a live line's width wraps that line once before the next redraw reads the new width, and leaves one stray line above the region.
- **A terminal narrower than 60 columns or shorter than 12 rows,** or one whose `TERM` is `dumb`, gets no live region. Its lines only settle: a stage's line prints as it starts and again as it settles, and a question prints the moment it's asked, with nothing redrawn. Under 60 columns the rail still draws at 60, so any line wider than the terminal wraps.
- **Emoji joined into one glyph** (a family, a flag) count as two cells, as the Unicode width tables say; a terminal that draws them wider overflows a body full of them.
- **A program that asks on the terminal mid-stage** (git for a credential, ssh for a passphrase, gpg for a PIN) is drawn over by the region's next redraw, as today's spinner drew over it; a credential helper, ssh-agent or a GUI pinentry avoids it.
- **A terminal made shorter mid-run** behaves as one made narrower: the next redraw can leave a stray line.
- **Ctrl-Z then `fg` mid-stage.** Mint leaves job control to the kernel, so the next redraw goes back over the region's height from wherever the shell left the cursor: it draws over the shell's `Stopped` and `fg` lines and leaves rows of the old region above (today's spinner left one stale line). Catching the stop to erase the region first was built and backed out: in an orphaned process group (mint run straight from `tmux new-session` or `ssh -t`) a caught stop freezes mint where the kernel would have dropped it.

## Build

Built without the `.workflows` pipeline, from this doc, as a stack of four PRs. Each gets two independent reviews as it's ready, and the whole change a stepped-up review before it's marked ready:

1. **The payloads.** The engine supplies the start and end stations, the plan's stages with their keys and the point of no return, stage keys, the unwind's fields and the next moves as lead and commands. Pretty still draws today's look from them, and plain stays byte for byte.
2. **The demo world and tapes,** recording today's look. This runs beside 1, so every later slice has the world to check itself against.
3. **The rail renderer and the live region,** built under `internal/presenter` and not yet wired in: colour levels and the accent, width, the rows, nodes, stations, hanging lines, questions, next and the close, the region writer, and the golden-frame harness.
4. **The switch,** one slice per command: release, then regenerate, then commit, init and version.
   - Each slice moves its verb's pretty output onto the rail, writes its golden frames, and records its tapes, which are checked by eye before review.
   - Until then a switched verb opts in through a transitional `WithRail()` on `NewForStartup`, every run ends with `presenter.Close`, and the engine's golden runs drive the real orchestrator onto the virtual terminal.
   - The last slice deletes today's pretty code with its dependencies, `WithRail()` and the fields only it read, so pretty mode is always the rail; it brings CLAUDE.md's presenter rules up to the live region, records the art and puts it in the README: the tour clip leads, and each command's section shows its still.
